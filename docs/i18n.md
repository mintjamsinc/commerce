# Commerce Webtop Internationalization (i18n)

How the Commerce Webtop apps (`commerce`, `commerce-dashboard`, `commerce-product`,
`commerce-products`, `commerce-customers`, `commerce-reports`, `commerce-oplog`,
`commerce-import`, `commerce-reconcile`, `commerce-events`)
present text, numbers, dates and currency in
the user's language and region. This is the authoritative reference for the
Commerce app suite; it mirrors the cms0 platform guidelines
(`cms0: documents/webtop-i18n-guidelines.md`) and is consistent with it by
design — Commerce apps run inside the same Webtop shell.

The platform supports **English (`en`)** and **Japanese (`ja`)** today, and is
built so that adding a locale is "drop in one JSON file" — no code change.

---

## 1. Why Commerce duplicates the composable

The Commerce app build is **self-contained**: its only build-time dependency is
the published `@mintjamsinc/ichigojs` runtime (see `webtop/rollup.config.js`).
It carries no cms0-internal imports — everything the shell provides
(`instance.api.*`, `window.appLaunch`, themes) is injected at runtime. So instead
of importing the shell's localization composable, Commerce ships its own copy at
`webtop/src/webtop/composables/use-localization.ts`. It is a faithful mirror of
the cms0 contract, with date formatting inlined (rather than pulled from the
shell's `Dates` util). **Keep the two in sync** when the shell contract changes.

At runtime the composable reaches the live shell services the same way every app
does:

| Service | Reached via | Provides |
| --- | --- | --- |
| `LocalizationManager` | `instance.api.localization` | effective locale, time zone, number-format locale, currency |
| `I18nService` | `instance.api.i18n` | `format(messageId, params, fallback, locale)` over the merged message bundles |

The shell broadcasts `localization-changed` (the user edited Preferences →
Localization) and `i18n-bundles-updated` (a bundle hot-reloaded) to every app
iframe; `handleLocalizationMessage` folds both into the app's reactive snapshot
so the UI re-localizes live.

## 2. Message bundles

### Layout — one file per app, merged by locale

The Commerce suite ships one bundle file **per app, per locale**, deployed to
JCR `/etc/i18n/` (repo path `etc/i18n/`):

```
etc/i18n/commerce.en.json            etc/i18n/commerce.ja.json
etc/i18n/commerce-dashboard.en.json  etc/i18n/commerce-dashboard.ja.json
etc/i18n/commerce-product.en.json    etc/i18n/commerce-product.ja.json
etc/i18n/commerce-products.en.json   etc/i18n/commerce-products.ja.json
etc/i18n/commerce-customers.en.json  etc/i18n/commerce-customers.ja.json
etc/i18n/commerce-reports.en.json    etc/i18n/commerce-reports.ja.json
etc/i18n/commerce-oplog.en.json      etc/i18n/commerce-oplog.ja.json
etc/i18n/commerce-import.en.json     etc/i18n/commerce-import.ja.json
etc/i18n/commerce-events.en.json     etc/i18n/commerce-events.ja.json
etc/i18n/commerce-publish.en.json    etc/i18n/commerce-publish.ja.json
```

The shell's `I18nService` derives a file's locale from the **last dot-delimited
segment** of its name (`commerce-product.ja.json` → `ja`) and **merges** every file
of the same locale into one bundle. This is the platform contract that lets the
cms0 core bundle (`en.json` / `ja.json`) and each Commerce app's bundle coexist
in `/etc/i18n/` without overwriting one another. Because each app owns a disjoint
key namespace, the merge never resolves a real conflict.

> This relies on the cms0 `I18nService` merge support. If you are on an older
> cms0 that keyed bundles by the whole file name (one file per locale,
> last-write-wins), Commerce bundles would collide with the core `en.json` —
> upgrade cms0 first.

### Key naming convention

Keys are hierarchical, dotted, **flat** (the JSON is not nested):

| Prefix | Owner | Example |
| --- | --- | --- |
| `common.*` | cms0 core — shared UI primitives | `common.save`, `common.close`, `common.minimize` |
| `app.<appId>.*` | one Commerce app; `<appId>` is the app folder name | `app.commerce-dashboard.card.sales` |

Commerce apps **reuse** the core `common.*` primitives (save / cancel / close /
minimize / maximize / ok / loading / search / …) rather than redefining them —
do not put `common.*` keys in a Commerce bundle. Everything else lives under the
app's own `app.<appId>.*` namespace, grouped by section/role
(e.g. `app.commerce-dashboard.card.*`, `.row.*`, `.unit.*`, `.statusbar.*`).

**App display title.** Each app localizes its window/start-menu title under
`app.<appId>.title` (resolved by the shell's `appTitle()` convention and used as
`instance.windowTitle`).

### Values are ICU MessageFormat

```json
"app.commerce-dashboard.kpi.revenue": "Revenue / {days}d",
"app.commerce-dashboard.pill.daysLeft": "{days}d left"
```

### Rules

- **Keep `en` and `ja` in sync.** Every key in an app's `*.en.json` must exist in
  its `*.ja.json` and vice versa. `en` is the ultimate fallback.
- **Never concatenate translated fragments.** One sentence per key, with
  placeholders; word order differs between languages.
- **Don't translate domain DATA.** Server-provided values — order/inventory
  status enums, product titles, SKUs, currency codes, channel names, server
  error strings — are content, not chrome. Leave them as the server sends them
  (the dashboard, for instance, still `humanize`s status keys client-side).

## 3. Using i18n from a Commerce app

`commerce-dashboard` is the canonical reference implementation. Wire it in four
places, then call the helpers from the template.

### 3.1 Import + snapshot

```ts
import {
  createLocalizationSnapshot, refreshLocalization, handleLocalizationMessage,
  translate, formatNumber, formatCurrency, formatDate,
} from '../../composables/use-localization.js';

// data()
localization: createLocalizationSnapshot(),
```

### 3.2 Refresh on launch + localize the window title

```ts
// in appLaunch(instance), after this.instance is assigned:
refreshLocalization(vm.localization, vm.instance);
instance.windowTitle = vm.t('app.commerce-dashboard.title', undefined, 'Commerce Dashboard');
```

### 3.3 Fold shell broadcasts into the snapshot

```ts
// in the window 'message' listener — handles locale change AND bundle reload:
if (handleLocalizationMessage(data.type, vm.localization, vm.instance)) return;
```

### 3.4 Thin method wrappers

```ts
methods: {
  t(id, params, fallback) { return translate(this.localization, this.instance, id, params, fallback); },
  fmtNumber(v, o)   { return formatNumber(this.localization, v, o); },
  fmtCurrency(v, o) { return formatCurrency(this.localization, v, o); },
  fmtDate(v, o)     { return formatDate(this.localization, v, o); },
}
```

### 3.5 Use them in the template

```html
<h2>{{ t('app.commerce-dashboard.card.sales') }}</h2>
<span>{{ fmtCurrency(order.total) }}</span>   <!-- effective currency -->
<span>{{ fmtDate(node.lastModified) }}</span> <!-- effective locale + zone -->
<button :title="t('common.close')">…</button>
```

`t()` always takes a key, never an English literal. Pass a `fallback` literal
only as a safety net while a key is being introduced.

> **Pitfall — never put an ICU message as an inline fallback inside `{{ }}`.**
> ichigojs ends an interpolation at `}}`, and an ICU plural/select message also
> ends with `}}`, which closes the interpolation early → *Unterminated string
> constant* at mount. Inside `{{ }}`, omit the inline fallback (the key resolves
> from the bundle): `{{ t('x.count', { count: n }) }}`. ICU-bearing fallbacks are
> fine in attribute bindings (`:title="…"`) or defined in `app.ts`.

### 3.6 Why it repaints automatically

ichigojs re-evaluates a binding when a reactive value it *read* mutates. Each
helper reads the snapshot field(s) it depends on (`locale`, `numberFormat`,
`currency`, `timeZone`, and an internal `revision` bumped on bundle reload), so
switching language in Preferences or hot-editing a bundle re-runs every `t()` /
`fmt*()` binding with no extra code in the app.

## 4. Adding a string (checklist)

1. Pick a key in the app's `app.<appId>.*` namespace (or reuse a `common.*`
   primitive).
2. Add it to **both** `etc/i18n/<appId>.en.json` and `<appId>.ja.json`.
3. Reference it via `t('your.key')` in the template (or `this.t(...)` in TS).
4. Never hardcode the English text in the component.

## 5. Adding a locale

Drop a new `<appId>.<locale>.json` (e.g. `commerce-dashboard.fr.json`) next to
the others with the same key set, for each app. No code change is required: the
loader derives the locale from the file name and the fallback chain is
`exact → language-only → en`.

## 6. Adding a new Commerce app

Wire the snapshot (§3), reuse `common.*`, add an `app.<newAppId>.title` plus its
keys to a new `etc/i18n/<newAppId>.{en,ja}.json` pair, and register the app in
`webtop/rollup.config.js`. Apps restored at startup may render once before the
bundles finish their initial load; the `i18n-bundles-updated` handling in
§3.3 repaints them when the bundles arrive.
